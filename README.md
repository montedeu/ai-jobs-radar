# Радар ML-исследований на arXiv

Сервис следит за потоком ML-статей на arXiv и отвечает, какие методы, модели, задачи и датасеты растут, а какие затухают. В разработке: расписание, сбор статей, база и MCP-сервер работают; извлечения сущностей и трендов ещё нет.

Независимый учебный проект; arXiv его не одобрял и не поддерживает.

Термины — в [`GLOSSARY.md`](GLOSSARY.md), ключевые решения — в [`docs/adr/`](docs/adr/).

## Как устроено

```
Cloud Scheduler ──▶ Cloud Run Job radar-collect ──▶ Postgres (Neon) ◀── Cloud Run radar-mcp ◀── Claude
  10:00 Астана,        radar daily                    журнал запусков        radar serve-mcp     (коннектор
  пн–пт                                                                      токен в заголовке    с токеном)
```

Один образ, одна команда `radar` с подкомандами:

| Команда | Что делает | Где работает |
|---|---|---|
| `radar migrate` | применяет миграции схемы | задача `radar-migrate`, шаг деплоя |
| `radar collect` | забирает статьи, появившиеся или изменённые с прошлого запуска | вручную, без извлечения; задача по расписанию запускает `radar daily` |
| `radar daily [--max-papers N] [--max-extract-papers N]` | сначала то же, что `radar collect`, затем шаг извлечения: забирает результаты всех отправленных пакетов (в том числе пакетов полного прогона), переключает текущий прогон на законченный полный (`runs.promote`) и отправляет текущим прогоном статьи среза, у которых нет отметки завершения с нынешним хешем аннотации (не отправляет статьи в пакетах `sending`/`submitted` и те, от которых прогон отказался). Каждый шаг пишет свою строку в журнал запусков (`collect`, `extract`), сбой одного не мешает другому; код выхода ненулевой, если упал любой. Строка `extract` хранит `collected`, `batches_collected`, `promoted`, `current_run`, `due`, `gave_up`, `submitted`, `spent_usd`. Нового прогона не начинает; пока текущего прогона нет, ничего не отправляет и клиента модели не создаёт. Статей к отправке больше `EXTRACTION_DAILY_MAX_PAPERS` (500): шаг падает с `TooManyPapers`, ничего не отправив. Так бывает в день переключения на полный прогон, если за время полного прогона накопилось больше `EXTRACTION_DAILY_MAX_PAPERS` статей: запуск повторяют с `--max-extract-papers N`. `--max-papers N` уходит в шаг сбора. Пакет, который не удалось забрать, записывается в `batch_errors` и не мешает остальным пакетам, переключению и отправке; шаг после них завершается ошибкой со списком пакетов. Отправка идёт частями по `EXTRACTION_BATCH_SIZE`: если потолок бюджета остановил её после части, ошибка говорит, сколько частей отправлено и сколько осталось. Клиенту модели нужен ключ Anthropic (`ANTHROPIC_API_KEY`); пока его нет в окружении задачи (подключение в #22), при наличии пакетов к сбору или статей к отправке шаг `extract` завершается статусом `skipped`, а код выхода 0 | задача `radar-collect` по расписанию |
| `radar backfill` | собирает историю по дням с 1 ноября 2025, продолжает с места остановки | та же задача, запуск вручную |
| `radar check-jobs` | проверяет, что задача сбора сможет стартовать; к arXiv не обращается | шаг деплоя |
| `radar frequencies --run N --out файл.md` | пишет в файл Markdown доли верхних сущностей прогона `N` среди статей среза с отметкой завершения в выбранном прогоне (`--category`, по умолчанию cs.CL; `--limit`, по умолчанию 40) с примерами аннотаций; колонки «фоновое», «узкие соседи» и «рекомендация» остаются пустыми, модель не вызывается | вручную |
| `radar full-run [--confirm [--restart | --abandon-sending]]` | без `--confirm` показывает план и оценку стоимости (токены считает настоящий клиент модели, это бесплатно) и ничего не отправляет и не создаёт; с `--confirm` создаёт полный прогон на всю собранную историю или продолжает самый новый незавершённый (только если у него та же модель и конфигурация запроса) и отправляет его пакетами по `EXTRACTION_BATCH_SIZE` статей. Подключается по прямому адресу базы и отказывает на адресе пулера; перед каждым пакетом проверяет, что прогон не заблокирован отказами и нет пакета в `sending`. Отказывает с кодом 1, если этот прогон заблокирован отказами, если у него есть пакет в `sending`, если новее его незавершённый прогон с другой конфигурацией, если история пуста или другая такая команда уже идёт; из тупика выводят `--abandon-sending` (только с `--confirm`: пакеты прогона в `sending` получают статус `abandoned`, `collect` их не трогает, их оценка остаётся в расходе) и `--restart` (только с `--confirm`, вместе с первым не работает): новый полный прогон, в том числе когда текущий прогон с той же конфигурацией. Проверка потолка бюджета — в `extraction.submit`, перед каждым пакетом; остановка на потолке оставляет отправленные пакеты. Результаты забирает и прогон переключает ежедневная задача (#27) | вручную, платное: запускает разработчик |
| `radar serve-mcp` | MCP-сервер на `$PORT`, путь `/mcp` | сервис `radar-mcp` |

MCP-сервер отвечает только на запросы с заголовком `Authorization: Bearer <токен>`; без токена открыт один путь `/health`. Пока в нём один инструмент, `service_status`: когда каждая задача запускалась в последний раз и чем закончилась, а по каждому срезу — число статей по месяцам, до какой даты собрана история (`collected_through`: позднее из границы дозагрузки и дня перед последним временем arXiv, до которого сбор дошёл; пока граница дозагрузки не записана, `null`) и дни без статей до неё; один раз на ответ — отметка последнего успешного ежедневного сбора и размер базы. Если сводку не удалось прочитать, в ответе остаётся `latest_runs`, а вместо `history` — `history_error`: тип ошибки и SQLSTATE, если он есть, без текста ошибки.

## Разработка

```bash
git config core.hooksPath .githooks
uv sync
uv run pytest          # поднимает встроенный Postgres, сеть и облако не нужны
uv run ruff check && uv run ruff format --check
```

Локальный запуск против своей базы:

```bash
export DATABASE_URL=postgresql://...
uv run radar migrate
uv run radar collect
MCP_TOKEN=dev uv run radar serve-mcp
```

Новая миграция — файл в `src/research_radar/migrations/versions/`, SQL пишется вручную:

```bash
uv run alembic -c alembic.ini revision --rev-id 0002 -m "описание"
```

## Облако

Разовая настройка — проект Google Cloud, WIF, секреты, база Neon, расписание:

```bash
./scripts/provision.sh
```

История собирается один раз, после первого деплоя (около 20 минут, лимит arXiv — запрос в три секунды):

```bash
gcloud run jobs execute radar-collect --args=backfill --region=europe-west1 --project=<проект> --wait
```

Сценарий настройки можно перезапускать: каждый шаг проверяет, что уже сделано. Секреты (строка подключения, токен MCP-сервера) хранятся только в Secret Manager.

Деплой — пуш в `main`: проверки, сборка образа, миграции отдельной задачей, затем задача сбора и MCP-сервер. Новая версия сервера сначала не получает трафика и включается только после проверки снаружи; при сбое трафик остаётся на прежней. Деплой включается переменной репозитория `DEPLOY_ENABLED`, которую сценарий настройки ставит последним шагом; до этого шаг деплоя пропускается.

### Подключение к Claude

1. Адрес сервера — в сводке запуска Deploy, вида `https://radar-mcp-….run.app/mcp`.
2. Токен: `gcloud secrets versions access latest --secret=mcp-token --project=<проект>`.
3. В Claude: настройки → коннекторы → добавить свой коннектор; адрес из п. 1, в заголовках запроса — `Authorization` со значением `Bearer <токен>`.
