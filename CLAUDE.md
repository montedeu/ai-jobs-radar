# ml-research-radar

Радар ML-исследований на arXiv: следит за потоком статей и отвечает, какие методы, модели, задачи и датасеты растут, а какие затухают. Термины — в `GLOSSARY.md`, ключевые решения — в `docs/adr/`. Срок сдачи — 30 ноября 2026.

## Категория 2: метод «Техлид»

Код пишет агент, решения и понимание принадлежат разработчику.

- Развилку с настоящими альтернативами агент выносит разработчику с рекомендацией и ждёт ответа; молча не выбирает.
- Документы приписывают разработчику только те причины, которые он назвал сам (`CODING_STANDARDS.md`). Довод агента записывается как наблюдение агента.
- В конце каждой недели — проверка понимания по принятым решениям (навык `understanding-check`), первая — в конце первой недели.

## Учебный островок: запрос роста

SQL-запрос роста (скользящие окна, доли, пороги, деление на растущие, новые и затухающие — ADR 0004) разработчик пишет сам. Файл — `src/research_radar/sql/growth.sql`, условие — `docs/growth-query.md`, тесты — `tests/test_growth.py`.

- Агент этот файл не редактирует, даже чтобы исправить опечатку, и не пишет решение или его части, даже по прямой просьбе.
- Проверяя тесты, агент может написать собственное решение вне репозитория и обязан удалить его сразу после проверки; в репозиторий и в сообщения оно не попадает.
- Агент даёт условие в терминах глоссария, тесты на маленьких наборах данных и обёртку на Python.
- Подсказки усиливаются только по просьбе разработчика: направление → понятие → разбор на похожем, но другом примере.
- Ревью запроса: упавшие тесты с причиной; ошибки, которые тесты не ловят, — каждая новым тестом, на котором запрос даёт неверный результат; улучшения (читаемость, лишние проходы, план выполнения с `EXPLAIN ANALYZE`) — с местом, следствием и доказательством, без исправленного SQL.
- Помесячный ряд агент пишет только после того, как запрос роста принят.
- Если запрос не готов к сроку, решение (сдвинуть демо или принять более сильную подсказку) принимает разработчик.

## Деньги и доступ

- Извлечение: Claude Haiku 5.5 через Batch API со структурированным выводом; потолок $20. Агент: старт на Haiku 5.5, потолок $5; подъём до Sonnet 5.5 — только по результату набора вопросов и с решения разработчика.
- Полный прогон запускается только по явной команде разработчика и только по всей обработанной истории. Ежедневная задача обрабатывает лишь новые статьи текущим прогоном.
- Перед каждым пакетом задача считает токены, складывает с уже потраченным и отказывается стартовать при выходе за потолок. У ежедневной задачи есть дневной предел на число статей.
- Два раздельных ключа Anthropic (извлечение и агент), предоплата без автопополнения. Ключи и токены — только в Secret Manager; секретов не больше пяти, старые версии отключаются сразу.
- MCP-сервер и агент отвечают только на запросы с токеном в заголовке. Один экземпляр на сервис, остановка при простое.
- Перед созданием ресурсов в Google Cloud проверить в консоли бесплатную норму Cloud Scheduler и учёт задач Cloud Run: по документации это подтвердить не удалось.

## Устройство

- Python 3.12, uv, ruff, psycopg 3 без ORM, pytest со встроенным Postgres — как в fraud-api. Схемы данных — Pydantic.
- Миграции — Alembic, пишутся вручную на SQL, применяются отдельным шагом деплоя; перед настоящей базой — на ветке Neon.
- Один пакет с командами (сбор, извлечение, MCP-сервер, агент, замер), один образ, три ресурса Cloud Run: задача и два сервиса. Деплой через GitHub Actions с WIF. Отдельные проекты в Neon и в Google Cloud.
- Сбор: Cloud Scheduler в 10:00 по Астане, пн–пт, команда `radar collect`. История — `radar backfill`, запускается вручную и продолжает с последнего законченного дня. Сбор и извлечение — раздельные шаги с собственными отметками; журнал запусков в базе.
- MCP-инструменты: `rising_entities`, `entity_stats`, `search_papers`. Категория и дата расчёта — параметры везде; cs.CL нигде не зашит. Имя сущности принимается в любом написании. В каждом ответе — шапка с датой расчёта, окнами, прогоном извлечения и границей обработанной истории; в ответах о трендах — статьи-примеры.
- Поиск статей — полнотекстовый в Postgres плюс фильтр по сущности; эмбеддингов в сервисе нет.
- Не используются: Label Studio, готовые клиенты arXiv, оркестраторы, Terraform, ORM.

## Порядок работ

1. Пустой каркас в облаке: задача, расписание, MCP-сервер с заглушкой за токеном, рабочий деплой.
2. Схема, сборщик на API arXiv (ADR 0003), первая выгрузка cs.CL с 1 ноября 2025. Условие и тесты для запроса роста — в первый день.
3. Пилот на 200 аннотациях в двух конфигурациях (с рассуждением модели и без), таблица частот, стоп-список, правила разметки с примерами из пилота.
4. Промежуточный прогон на 3–4 тысячах аннотаций равномерно по месяцам: форма трендов и строгость порога до полного прогона.
5. Разметка эталона вслепую; полный прогон.
6. Нормальная форма, словарь, тренды, три инструмента, замер метрики — точка демо.
7. Агент, отладочный набор, сравнение моделей (Haiku 5.5, DeepSeek, одна открытая), кандидаты в словарь по эмбеддингам имён.
8. Набор из 15 вопросов, документация, запас.

При нехватке времени выбрасывается в таком порядке: сравнение моделей, эмбеддинги для синонимов, `entity_stats`, подъём агента до Sonnet. Не выбрасываются: метрика извлечения, проверка ссылок, автоматический сбор.

## Известные ограничения, которые сервис оговаривает сам

- «Растёт» означает «чаще упоминают в аннотациях», не «чаще применяют».
- Иерархии сущностей нет.
- Цифры качества относятся к cs.CL и к прочтению правил одним разметчиком.
- Нельзя выдавать проект за одобренный arXiv.
