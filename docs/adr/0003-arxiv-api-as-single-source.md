# Один источник статей — обычный API arXiv, и для истории, и для ежедневного сбора

Статьи берутся из API arXiv (`export.arxiv.org/api/query`). История собирается один раз запросами по дням подачи, начиная с 1 ноября 2025. Ежедневная задача читает статьи среза в порядке «последние обновлённые первыми» и останавливается там, где начинался её прошлый запуск, с перекрытием в один день; так она получает и новые статьи, и новые версии старых. Статья определяется идентификатором arXiv без номера версии; повторный приход обновляет запись.

## Как решение менялось

- Исходный замысел разработчика: история из снимка Kaggle один раз, дальше OAI-PMH.
- В сессии проектирования 10 ноября 2026 разработчик по рекомендации агента принял один источник — OAI-PMH. Довод агента: два источника означали бы два разбора к одной схеме и шов между датой снимка и первым ежедневным сбором.
- В тот же день проверка на живом сервисе показала две проблемы (см. наблюдения ниже). Агент рекомендовал перейти на обычный API сразу; разработчик согласился.

## Наблюдения агента 10 ноября 2026

- **В основном формате OAI-PMH нет даты первой версии.** Для статьи 1706.03762 поле `created` формата `arXiv` равно 2023-08-02 (дата седьмой версии), первая версия вышла 2017-06-12. Проверено на одной записи.
- **OAI-PMH не отдавал записи.** `Identify`, `ListSets` и `ListMetadataFormats` отвечали за доли секунды; `GetRecord` и `ListRecords` в форматах `arXiv` и `arXivRaw` около трёх минут не отвечали и завершались кодом 503, позже 429 с телом «Rate exceeded», при одном запросе раз в 20 минут. Наблюдение длилось около двух часов; формат `arXivRaw`, где должна быть история версий, увидеть не удалось.
- **Обычный API отвечал и отдаёт нужное.** Запрос статей cs.CL за один день подачи: 0,8 секунды, 95 статей, среди них те, у которых cs.CL — дополнительная категория; поле `published` — дата первой версии и у статей во второй версии.
- **Диапазон по `lastUpdatedDate` правок не находит**: запрос с ним вернул те же 95 статей, что и запрос по `submittedDate`, и ни одной статьи, поданной раньше. **Сортировка по `lastUpdatedDate` находит**: из 300 последних записей cs.CL 135 были новыми версиями более ранних статей.
- **Пробный запуск сборщика на настоящем API**: первый ежедневный запуск — 772 записи за 4 запроса и 11 секунд; три дня истории — 134 статьи за 3 запроса; повторный ежедневный запуск — 1 запрос, ни одной изменённой строки.

## Рассмотренные варианты

- **`arXivRaw` через OAI-PMH.** Отклонено: формат не удалось получить, а надёжность сервиса под вопросом, даже если он восстановится.
- **Статьи через OAI-PMH, дата первой версии через API.** Отклонено: раз API отдаёт и статьи, и дату, второй источник не нужен.
- **Дата из идентификатора статьи.** Отклонено: точность до месяца, а окна считаются по дням.
- **Снимок Kaggle.** Остаётся запасным вариантом для истории, если API перестанет её отдавать.

## Следствия

- Лимит arXiv — один запрос в три секунды по одному соединению, общий на все машины. История за год — около 375 запросов, примерно 20 минут.
- Глубокая постраничная выдача API ненадёжна: под нагрузкой страница может прийти пустой. Поэтому история идёт по дням, где результат помещается в одну страницу, а пустая страница при ненулевом остатке запрашивается повторно. Ответ «статей ноль» принимается только со второго раза: иначе день был бы отмечен собранным и к нему никто бы не вернулся.
- Задачи сбора не работают одновременно: лимит arXiv — одно соединение на всё, что запускает проект.
- Отбор идёт по времени UTC: дата статьи — дата `published` в UTC.
- Хранится последняя аннотация; дата статьи — всегда дата первой версии. Извлечение повторяется только при изменении текста аннотации (сравнение хеша), поэтому переписанная аннотация может изменить долю за прошлые месяцы на несколько статей задним числом.
- Если статье добавили категорию cs.CL без новой версии, ежедневная задача увидит её, только если arXiv при этом сдвинул дату обновления; это не проверено.
- Новая версия статьи, первая версия которой старше начала истории, не сохраняется.
- История начинается 1 ноября 2025 и растёт; старое не удаляется. От глубины в 24 месяца разработчик отказался в сессии: «я думаю, что это слишком много».
- Срез категории — все статьи, у которых она есть среди категорий, основной или дополнительной. Срезы пересекаются, итог по нескольким считается по различным статьям.
